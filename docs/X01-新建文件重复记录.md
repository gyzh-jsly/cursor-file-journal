# 问题复盘：新建文件出现重复记录 / 文件名错误
行为：新建22.txt。结果：数据库中插入数据字段file_name为新建数据库.txt，刷新网页，正常显示数据库内容。和上方“报错：发现新文件，已纳入管理: 1.txt……”这里报错一致，不过1.txt那次，好歹名字是对的，这次名字都不对。

## 一、问题现象

1. **重复记录**：在监视文件夹中新建一个文件（如 `22.txt`），软件聚合流页面出现了两个文件记录：`新建文本文档.txt` 和 `22.txt`
2. **文件名错误**：数据库中实际存储的文件名是 `新建文本文档.txt`，而不是用户最终命名的 `22.txt`
3. **控制台报错**：`DuplicateKeyException: Duplicate entry '...' for key 'watched_file.file_path'`

---

## 二、问题根源

### Windows 新建文件的底层流程
1. 用户右键 → 新建 → 文本文档
2. 系统立即创建一个物理文件，默认名为 `新建文本文档.txt`
3. 系统自动进入重命名编辑状态
4. 用户输入新名称（如 `22.txt`）并回车
5. 系统执行文件重命名操作

### 软件的错误响应
- `WatchService` 监听到了 `ENTRY_CREATE` 事件，在 **步骤 2** 就将 `新建文本文档.txt` 插入了数据库
- 当文件重命名为 `22.txt` 后，`WatchService` 又收到一个事件，再次尝试插入，导致唯一键冲突
- 由于数据库中已经存在 `新建文本文档.txt` 这条记录，而软件**没有处理重命名后的文件名更新**，导致最终显示的文件名仍是 `新建文本文档.txt`

---

## 三、根本原因

`FileWatchService` 中的 `handleFileEvent` 方法缺少有效的防重复插入逻辑，具体表现为：
- 没有检查物理文件是否真实存在（临时文件被当作正式文件处理）
- 没有在插入前查询数据库确认记录是否已存在
- 没有对并发事件做同步控制，导致多个事件同时处理同一文件

---

## 四、解决方案

在 `FileWatchService.handleFileEvent` 方法中增加以下防护机制：

| 防护层 | 实现方式 | 作用 |
|:---|:---|:---|
| **物理文件校验** | `file.exists() && file.isFile()` | 过滤掉已被重命名或删除的临时文件 |
| **并发控制锁** | `ConcurrentHashMap<String, Boolean>` | 防止同一文件路径被多个线程同时处理 |
| **数据库去重查询** | `fileMapper.selectByFilePath(absolutePath)` | 插入前二次确认数据库中是否已有记录 |
| **唯一键冲突兜底** | `catch (DuplicateKeyException e)` | 即使前面的防护全部失效，也不会导致线程崩溃 |
| **处理标记清理** | `finally { processingFiles.remove(...) }` | 确保锁被正确释放，不影响后续事件 |

### 核心代码片段

```java
private void handleFileEvent(Path filePath) {
    File file = filePath.toFile();
    String absolutePath = file.getAbsolutePath();

    // 1. 物理文件校验
    if (!file.exists() || !file.isFile()) {
        return;
    }

    // 2. 并发控制
    if (processingFiles.putIfAbsent(absolutePath, Boolean.TRUE) != null) {
        return;
    }

    try {
        // 3. 数据库去重
        WatchedFile existing = fileMapper.selectByFilePath(absolutePath);
        if (existing != null) {
            return;
        }

        // 4. 插入新记录
        WatchedFile newFile = new WatchedFile();
        newFile.setFilePath(absolutePath);
        newFile.setFileName(file.getName());
        // ... 其他字段设置
        fileMapper.insert(newFile);
        
    } catch (DuplicateKeyException e) {
        // 5. 唯一键冲突兜底
        System.out.println("文件已存在，忽略");
    } finally {
        // 6. 释放锁
        processingFiles.remove(absolutePath);
    }
}



## 五、修复后的效果
1.新建文件时，临时文件名`新建文本文档.txt`被正确过滤，控制台输出`文件已在数据库中，跳过`
2.最终的真实文件名`33.txt`被正确识别并插入，控制台输出`✅ 发现新文件，已纳入管理`
3.不再出现重复记录和`DuplicateKeyException`报错

## 六、关于"反应延迟"的说明
WatchService 的响应时间取决于操作系统的文件事件通知机制，通常有 几百毫秒到 1~2 秒 的延迟，这是正常现象，并非代码性能问题。如需更实时的响应，可考虑用轮询方式作为补充，但会增加 CPU 开销，当前方案已能满足日常使用需求。
